Getting up to speed with mise

mise (pronounced “meez”, short for the French kitchen term mise-en-place — “everything in its place”) sets up your dev environment so every tool, variable, and task is exactly where it should be the moment you cd into a project. It’s one binary that replaces asdf, nvm, pyenv, direnv, and a bit of make.

one binary · 3 jobs config: mise.toml formerly rtx written in Rust
install
# the one-liner (or: brew install mise · apt · winget · cargo install mise)
$ curl https://mise.run | sh

the mental model

One tool, three jobs

Everything mise does falls into three buckets. The same mise.toml file drives all three, so a single committed config gets a teammate a byte-for-byte identical setup.

Tool versions

Installs and pins the exact version of node, python, go, terraform… per project. Your node becomes whatever the project says.

[tools] node = "20"

Environment

Sets and clears env vars as you enter and leave a directory — like direnv, built in. Load a .env, add to PATH, or set values inline.

[env] NODE_ENV = "dev"

Tasks

A project task runner — define build, lint, test once, with dependencies, and run them with the right tools already on PATH.

mise run build

how it hooks in

How mise gets onto your PATH

mise doesn’t patch your binaries — it puts the right versions in front of everything else on PATH. You wire it into your shell once; after that it re-evaluates on every prompt.

1 Add the hook, once

Append eval "$(mise activate zsh)" to ~/.zshrc (or bash/fish). This registers a hook that runs right before each shell prompt.

2 You cd or open a shell

The hook fires. mise looks for config files starting in the current directory and walking up to /, plus your global config.

3 It resolves versions & env

Every pinned tool’s bin/ directory gets prepended to PATH, and [env] vars are exported (and un-exported when you leave).

✓ node is the pinned version

Now which node points at ~/.local/share/mise/installs/node/20/bin/node — no version-manager subshell, no manual switching.

Two ways to resolve: activate vs shims

There are two mechanisms. Most people use activate for interactive shells and let shims cover everything else.

~/.zshrc
eval "$(mise activate zsh)"

Rewrites PATH on every directory change. Fast, always current, and which node shows the real path. The catch: it only runs in an interactive shell that sourced the hook.

PATH
# shim dir on PATH; each shim
# dispatches to the right version
~/.local/share/mise/shims/node

Small wrapper executables that forward to the correct version. They work anywhere PATH is read — IDEs, cron, CI, non-interactive scripts — but are a touch slower and need a mise reshim when a tool adds new binaries.

the config file

Anatomy of a mise.toml

One TOML file, four sections you’ll actually use. Drop it in a project root, commit it, and everyone who trusts it gets the same tools, env, and tasks.

[tools] — versions to install [env] — environment variables [tasks] — project commands [settings] — mise behavior
mise.toml
[tools]
node = "20"              # latest 20.x
python = "3.12"
terraform = "1.7.5"       # exact pin
go = "latest"
"npm:prettier" = "latest"  # backend:tool — npm, cargo, pipx, ubi, aqua…
[env]
NODE_ENV = "development"
_.file = ".env"            # load vars from a dotenv file
_.path = ["./bin"]         # prepend project ./bin to PATH
[tasks.build]
run = "npm run build"
depends = ["lint"]         # run lint first

[tasks.lint]
run = "eslint ."
[settings]
experimental = true

Trust before it runs. Because a config can set env vars and run hooks, mise refuses to load an unfamiliar one until you mise trust it. Clone a repo, and its mise.toml stays inert until you say so — so a malicious project can’t silently inject PATH or secrets.

which config wins

Config resolution & precedence

mise merges every config it finds from your current directory up to the filesystem root, then your global config underneath. When two set the same key, the one nearest your directory wins, and a .local file beats its committed sibling. (Hover a layer.)

./mise.local.tomlyour machine only · git-ignored · highest
./mise.tomlthe project · committed & shared
../mise.tomla parent directory · monorepo defaults
~/.config/mise/config.tomlglobal · your personal baseline
wins

Two more knobs: a .tool-versions file (asdf’s format) is still read for compatibility, and environment-specific configs load when you set MISE_ENV — e.g. mise.production.toml layers on top when MISE_ENV=production. Run mise config to see exactly which files are active and in what order.

step by step

What happens when you cd project/

  1. The prompt hook fires

    Your shell is about to draw a prompt; the hook installed by mise activate runs first.

  2. mise finds the configs

    It collects mise.toml and friends from here up to /, plus the global config, and merges them by precedence.

  3. Missing tools? It tells you

    If a pinned version isn’t installed yet, mise warns (or auto-installs, depending on settings). mise install fetches everything the config asks for.

  4. PATH & env are rewritten

    Each tool’s bin/ is prepended to PATH, and [env] vars are exported. Leaving the directory reverses it cleanly.

  5. You just… work

    node, python, terraform now resolve to the project’s versions. No subshell, no nvm use, nothing to remember.

the cheat sheet

Commands to get up to speed

CommandWhat it does
mise use node@20Add a tool to mise.toml here and install it. Add -g for your global config.
mise installInstall every tool the active config pins (great first step in a fresh clone).
mise ls / mise currentShow installed tools / the versions active right now.
mise ls-remote nodeList every version available to install for a tool.
mise exec node@22 -- node -vRun a one-off command under a specific version without changing config.
mise run buildRun a task from [tasks] (with its depends first). mise tasks lists them.
mise trustMark the current directory’s config as trusted so mise will load it.
mise configShow which config files are active, and in what precedence.
mise doctorDiagnose setup problems — activation, shims, PATH, plugins.
mise upgradeBump installed tools to the newest allowed by each version spec.

why bother

What it replaces

The pitch is consolidation: one config, one tool, instead of a pile of single-purpose managers that each need their own setup and shell hook.

Instead of…mise gives you…
nvm, pyenv, rbenvOne version manager for every language, sharing the asdf plugin ecosystem plus faster core backends.
asdfA drop-in with .tool-versions compatibility, but written in Rust (much faster) and no per-tool shims by default.
direnvBuilt-in per-directory env vars and dotenv loading via [env].
make, justA task runner in the same file, with dependencies and your pinned tools already on PATH.

reference

Where config lives

mise recognizes a whole family of filenames so it slots into existing conventions. The common ones:

PathRole
mise.toml · .mise.tomlProject config. Committed to the repo.
mise.local.tomlPersonal overrides for this project — git-ignore it.
mise.{env}.tomlEnvironment-specific, loaded when MISE_ENV matches (e.g. mise.production.toml).
~/.config/mise/config.tomlYour global baseline across every project.
.tool-versionsLegacy asdf format — read for compatibility.
